# Spike S3 — Starlight + versionado manual (API real)

No se ejecutó como spike aislado desechable (el plan original lo preveía así); se verificó de
forma empírica directamente contra `apps/docs` durante la implementación real de las Fases 2-5,
con cada hallazgo corregido en el momento. Se documenta aquí porque la Fase 1 exige este informe
como salida formal.

## 1. Mecanismo de exclusión de Pagefind — RESUELTO

**Campo real:** `pagefind: false` (booleano, nativo de `docsSchema()` de Starlight — no requiere
extensión de esquema). Confirmado en `starlight.astro.build/reference/frontmatter/`.

**Camino recorrido:** la primera implementación usó un campo inventado `pagefindExclude: true`
(vía extensión de esquema). Verificado empíricamente que **no hacía nada**: con una versión
archivada de prueba, Pagefind indexó 89/89 páginas (todas, incluidas las archivadas). Corregido a
`pagefind: false`; reverificado: `pagefind-entry.json` reportó `page_count: 44` (solo la versión
actual) tras el fix.

## 2. Slot de override para selector de versión — RESUELTO

**Componente real:** `SiteTitle` (confirmado en `starlight.astro.build/reference/overrides/`, lista
completa de componentes overridables verificada por fetch directo a la documentación oficial).

**Camino recorrido:** la primera implementación de `VersionSelect.astro` renderizaba
`<Default {...Astro.props} />` (el patrón documentado oficialmente) dentro del override — causó
`RangeError: Maximum call stack size exceeded` en el build estático (recursión). Corregido
reconstruyendo el enlace de título mínimo a mano en vez de renderizar el `Default` original.
**No resuelto el porqué exacto de la recursión** — podría ser un problema de esta versión concreta
de Starlight (0.41.11) con el patrón de ejemplo de su propia documentación; no se investigó más
allá porque la solución alternativa (no usar `Default`) es simple y funciona.

## 3. Sintaxis de grupo de sidebar con `autogenerate` — RESUELTO (no estaba en el paquete de evidencia)

**Forma real:** `{ label, collapsed, items: [{ autogenerate: { directory } }] }` — un `autogenerate`
anidado dentro de `items`, no una propiedad de primer nivel del grupo.

**Camino recorrido:** dos intentos fallidos con formas razonables pero incorrectas
(`{ label, collapsed, autogenerate: {...} }` y `{ label, autogenerate: { directory, collapsed } }`),
ambos con errores de Astro suficientemente descriptivos para corregir en el acto. El segundo error
citó literalmente el ejemplo correcto ("Support for autogenerated sidebar groups was removed in
Starlight v0.39.0").

## 4. Convención de slug para páginas `index.md` — RESUELTO (no estaba en el paquete de evidencia)

Un `index.md` dentro de una carpeta resuelve al slug de la carpeta (`referencia/herramientas`), no
a `referencia/herramientas/index`. El guardarraíl `check-coverage.mjs` verificaba solo existencia de
fichero (pasaba), pero Astro rechazaba el slug real del sidebar en build (`astro build`, no
`check-coverage`). Corregido: 7 slugs de sidebar ajustados y `check-coverage.mjs` actualizado para
probar también `<slug>/index.md` como candidato válido.

## 5. Restricción de slug con puntos — DESCUBIERTO EN ESTA FASE (no anticipado)

Astro sanea los puntos al generar el slug final de una carpeta de contenido: `1.0.0-test` se sirve
como `/100-test/`, no `/1.0.0-test/` — reproducido con 404 real vía Docker antes de identificar la
causa. **Implicación de producto:** los identificadores de versión de la documentación no pueden
usar el formato semver con puntos tal cual (`1.0.0`); deben usar guiones (`v1-0-0`). Documentado en
`conceptos/versionado.md`, `apps/docs/README.md`, y aplicado como validación dura en
`freeze-version.mjs` (el regex de slug ya no acepta `.`).

## 6. Integración de Svelte — NO EVALUADO

No se instaló `@astrojs/svelte` ni se probó ninguna isla interactiva — ninguna página de esta
entrega la necesitó (contenido estático). Queda sin verificar si `svelte@^5.43.6` (peer de
`@astrojs/svelte@9.0.1`) convive sin conflicto con la versión de Svelte que ya usa `apps/web` en el
mismo workspace pnpm — repetir esta verificación antes de la primera página que realmente necesite
una isla Svelte.

## 7. Hallazgo no previsto: bug de CSS en `brand.css`

No es parte de la API de Starlight, pero se descubrió y corrigió en el mismo ciclo de trabajo:
`--sl-color-white` es un token semántico interno que Starlight usa para el texto de las etiquetas de
grupo grandes del sidebar (`.group-label .large`) — redefinirlo a un valor "blanco" propio
(`var(--mc-neutral-0)`, que YA es blanco) no cambiaba el valor, pero el hecho de tocar ese token
específico rompía el contraste esperado por el CSS interno de Starlight en modo claro, dejando texto
blanco sobre fondo blanco (invisible) en las etiquetas de grupo y en enlaces con hover. Verificado
visualmente con captura de pantalla real (Chrome) antes y después del fix. Corregido eliminando esa
línea de `brand.css` — no hacía falta redefinir ese token para el theming de marca pretendido.

## Conclusión

Ninguno de los 4 `[POR VERIFICAR]` originales del plan quedó sin resolver; los 4 se resolvieron por
prueba empírica directa contra el sitio real (build real, Docker real, navegador real), no por
lectura de documentación únicamente. Se descubrieron 2 problemas adicionales no anticipados por el
paquete de evidencia original (restricción de puntos en slugs, bug de CSS de `--sl-color-white`),
ambos corregidos y documentados.
